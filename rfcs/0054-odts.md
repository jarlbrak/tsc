## Summary

Contracts carry taxonomy terms — `classification: customer_content.contact_information`, `sensitivity: restricted` — but the taxonomy those terms come from has no machine-readable form, so no tool can verify a cited term exists or apply the ordering rules governance hangs on it. ODTS is a YAML format (`kind: DataTaxonomy`) publishing a taxonomy as a self-contained, named, versioned artifact whose declared **type** — `flat`, `hierarchical`, or `ranked` — carries its validation semantics, plus a companion `kind: TaxonomyMapping` for cross-taxonomy alignments. ODTS defines mechanics, not vocabulary: how a taxonomy is documented, never which one to use. It is the artifact [RFC-0038](approved/odcs-v3.2.0/0038-context.md)'s `type: Taxonomy` links and [RFC-0053](https://github.com/bitol-io/tsc/pull/81)'s `taxonomies` declarations resolve to, changing neither.

## Motivation

Regulatory obligations attach to data through taxonomy terms, yet the taxonomy itself is documented for humans only — ISO/IEC 19944-1 is PDF prose; internal taxonomies live in wikis and spreadsheets. The consequences are mechanical. A misspelled term validates everywhere, because nothing machine-readable says what the valid terms are. Sensitivity schemes are overwhelmingly stack-ranked, and aggregates are handled at the highest tier present — the rule NIST FIPS 200 names the *high water mark* — but no artifact states the order, so the rule is enforced in review meetings, not CI. Terms are renamed and retired with no versioning contract, so citations drift silently.

The closest artifacts confirm the gap: Fideslang (under the IAB Tech Lab Privacy Taxonomy) is YAML with dot-path keys and per-term lifecycle, but no envelope — no in-file name, version, or structural declaration; W3C SKOS has hierarchy and mapping vocabulary, but no ordinal semantics, no versioning beyond convention, no conformance contract for a CI gate. The reference seam already exists: [RFC-0038](approved/odcs-v3.2.0/0038-context.md) (approved) introduced links of `type: Taxonomy`, and [RFC-0053](https://github.com/bitol-io/tsc/pull/81) (pending) names and versions a contract's schemes, leaving verification to tooling "when the referenced taxonomy is machine-readable". ODTS is what makes it machine-readable, and it works from the approved RFC-0038 anchor alone.

Taxonomy types are the core of the design: a code list needs membership checks only; a category tree adds hierarchy; a ranked scheme adds an order carrying the high-water-mark rule. The type is declared per taxonomy, in the taxonomy artifact — never in ODCS or ODPS, whose elements just carry terms. Guiding values: small, interoperable, non-breaking, AI-ready (definitions and criteria ground a classifier, and its citations get checked).

## Design and examples

An ODTS document is a YAML file of one of two kinds; recommended (non-normative) suffix: `.odts.yaml`.

### `kind: DataTaxonomy`

| Key | Type | Required | Description |
|---|---|---|---|
| `apiVersion` | string | Yes | ODTS standard version, e.g. `v0.1.0`. |
| `kind` | string | Yes | `DataTaxonomy`. |
| `name` | string | Yes | Machine reference name; the value contracts cite (e.g. `corp-edt`). |
| `version` | string | Yes | Taxonomy version (semver; see *Versioning*). |
| `type` | string | Yes | `flat`, `hierarchical`, or `ranked`. |
| `dimension` | string | No | Citing slot served; recommended `classification`, `sensitivity`; open (see *Dimensions*). |
| `title`, `id`, `status`, `description` | | No | Display name; stable registry identifier; lifecycle; human context. |
| `authoritativeDefinitions`, `tags`, `customProperties` | | No | Standard blocks. |
| `terms` | array | Yes | The taxonomy's terms. |

### Terms

| Key | Type | Required | Description |
|---|---|---|---|
| `term` | string | Yes | The term key — the exact value elements carry. Dot-separated segments of `[a-z0-9_]+`; unique within the taxonomy. |
| `name`, `description`, `examples`, `criteria` | | No | Label; definition; instances covered; conditions for applying the term. |
| `rank` | integer | For `ranked` | Position in the order; required for every term when `type: ranked`, not permitted otherwise. |
| `deprecated`, `replacedBy` | string | No | Version of deprecation; successor key (requires `deprecated`). |
| `baseline` | object | No | Expected term in another taxonomy: `{taxonomy, term}`. |
| `regulatory` | array | No | `{regime, citation?, note?}`, `regime` required. |
| `customProperties` | array | No | Standard block. |

Term identity is positional: taxonomy `name` + `version` + term key. In `hierarchical` taxonomies the key encodes the hierarchy — the parent is the key minus its final segment, every dot-prefix must exist, single-parenthood holds by construction. In `flat` and `ranked` taxonomies, dots carry no structural meaning.

### Taxonomy types

| Type | Structural rules | Validation semantics |
|---|---|---|
| `flat` | Unique term keys. | Membership; deprecation warnings. |
| `hierarchical` | Unique keys; every dot-prefix exists as a term. | Membership; deprecation warnings; prefix integrity. |
| `ranked` | Unique keys; every term carries an integer `rank`. | Membership; deprecation warnings; rank consistency. |

A sensitivity scheme is not a special construct: it is simply a ranked taxonomy. Greater rank outranks lower; ties are permitted (the IAB Tech Lab's 1–3 sensitivity scoring maps directly); values carry no meaning beyond order, so gaps (`100/200/300`) leave room for insertions. Future RFCs may add types; a taxonomy has exactly one.

### Dimensions

A taxonomy MAY declare the `dimension` it serves, and dimension names are unified with the citing slots they fill: a slot binds to the dimension of the same name. This makes cross-dimension misuse detectable (a sensitivity term sitting member-valid in the `classification` slot) and unprefixed terms resolvable when exactly one declared taxonomy carries the slot's dimension. Dimensions beyond ODCS's two field names need no new fields — citations ride in element-level custom properties of the same name:

| Dimension | Citing slot in ODCS |
|---|---|
| `classification` | The `classification` field |
| `sensitivity` | The `sensitivity` field |
| Any other, e.g. `data_use` | An element-level customProperty named `data_use` |

```yaml
customProperties:
  - property: data_use
    value: [corp-data-use:provide.secure, corp-data-use:improve]
```

### Versioning

Semver with normative meaning. MAJOR: anything that can invalidate a citation or flip a validation outcome — removing or renaming a term, reordering existing ranks, changing `type` or an existing `dimension`. MINOR: additive — adding or deprecating terms, inserting ranks, adding `baseline`/`regulatory`, declaring a `dimension`. PATCH: editorial. A term deprecates in place (`deprecated` + `replacedBy`); validators accept it and warn, naming the successor. Same MAJOR guarantees every cited term still resolves.

### Baseline and regulatory annotations

A `baseline` names the term elements classified with this one are expected to carry in another dimension; a differing value is a deviation — validators SHOULD warn and MUST NOT fail, so reviewed exceptions stay legitimate but visible. `regulatory` entries let tooling answer "which terms trigger regime X"; `regime` is a free string — ODTS imposes no vocabulary of regimes, consistent with imposing none of terms.

### `kind: TaxonomyMapping`

Cross-taxonomy equivalence is published once, centrally — never per-element in contracts. A mapping document declares `from` and `to` taxonomies by `{name, version, url?}` and versions independently of both, so a third party can map taxonomies it owns neither of. Entries are `{term, to, relation, note?}`, `relation` one of `exact`, `close`, `broader`, `narrower`, `related` — the semantics of SKOS's five mapping properties, describing the target relative to the source.

### Referencing taxonomies

Nothing changes in ODCS or ODPS: an ODTS artifact is the resolvable target of the references that already exist, self-identifying through its envelope — a declared `name`/`version` MUST equal the resolved envelope. A `url` fetches directly (the direction [RFC-0009a](approved/odcs-v3.1.0/0009a-ref-identify-external-contract.md) chose); `name`+`version` alone resolves via a catalog (the shape ODPS `contractId` assumes). Unrecognized targets remain documentation links.

### Validation semantics

This RFC specifies validation semantics, not a tool. A conforming validator:

1. MUST reject artifacts with duplicate term keys, missing dot-prefixes (`hierarchical`), missing or extra `rank` (`ranked`), or `replacedBy` without `deprecated` or naming a nonexistent term.
2. MUST verify mapping endpoints exist in the declared taxonomy versions, when resolvable.
3. MUST verify term membership for every citation. A citation is the value of any slot binding to a dimension by name (in ODCS, `classification` and `sensitivity`) or of an element-level custom property named for a declared taxonomy's `dimension`; list values check element-wise.
4. MUST verify declared `name`/`version` against the resolved envelope.
5. For `ranked` taxonomies, MUST verify rank consistency: an aggregate's term sits at the highest rank present among its members' terms (in ODCS: schema object over its properties; the same rule at any term-carrying aggregation level, including a future ODPS product over its contracts' elements).
6. SHOULD warn on deprecated citations (naming the successor), `baseline` deviations (never fail), and cross-dimension misuse; SHOULD resolve unprefixed terms against the single declared taxonomy of the slot's dimension — making [RFC-0053](https://github.com/bitol-io/tsc/pull/81)'s "exactly one applicable declaration" computable without amending it.

Failures on rules 1–5 fail CI on the pull request introducing the change.

### Example

```yaml
apiVersion: v0.1.0
kind: DataTaxonomy
name: corp-tiers
version: 2.0.0
type: ranked
dimension: sensitivity
description: Handling tiers; greater rank means stricter handling.
terms:
  - {term: public, rank: 100}
  - {term: internal, rank: 200}
  - {term: confidential, rank: 300}
  - {term: restricted, rank: 400, description: Severely harmful if disclosed.}
```

```yaml
apiVersion: v0.1.0
kind: DataTaxonomy
name: corp-edt
version: 4.2.0
type: hierarchical
dimension: classification
terms:
  - term: customer_content
    description: Data customers provide to, store in, or process in the service.
  - term: customer_content.contact_information
    description: Data that directly identifies or contacts a person.
    baseline: {taxonomy: corp-tiers, term: restricted}
    regulatory:
      - {regime: GDPR, citation: Art. 4(1)}
  - term: derived_data
  - term: derived_data.usage_metrics
    deprecated: "4.1.0"
    replacedBy: derived_data.telemetry
  - term: derived_data.telemetry
```

A contract declares both (via [RFC-0053](https://github.com/bitol-io/tsc/pull/81)'s block or [RFC-0038](approved/odcs-v3.2.0/0038-context.md) anchors):

```yaml
taxonomies:
  - {name: corp-edt, version: "4.2.0", url: https://example.com/corp-edt.odts.yaml}
  - {name: corp-tiers, version: "2.0.0", url: https://example.com/corp-tiers.odts.yaml}
```

Against a schema object at `sensitivity: corp-tiers:internal`: citing `corp-edt:customer_contnt.contact_info` fails CI (no such term); adding a `corp-tiers:restricted` property fails rank consistency; `derived_data.usage_metrics` warns, naming `derived_data.telemetry`; a `contact_information` column at `internal` draws a baseline-deviation warning, never a failure; `classification: corp-tiers:restricted` draws a cross-dimension warning.

### Out of scope for v1

Classification-policy rules (column-name patterns that auto-assign terms — classifier input, not contract validation); inheritance between artifacts (a derived taxonomy copies what it adopts, declares the derivation, and publishes a `TaxonomyMapping`; every artifact stays self-contained); additional types (the `type` field is the extension point).

## Alternatives

1. **Adopt SKOS.** This RFC adopts its mapping-property semantics, but rejects it as the format: no ordinal construct, lifecycle and versioning by publisher convention, no formal conformance for a CI gate, RDF-native with no standard YAML serialization.
2. **Extend OSDS ([RFC-0044](0044-osds.md)).** Complementary by OSDS's own design: OSDS defines reusable semantic definitions and links out to vocabularies; a governed taxonomy is a closed, versioned term-set with whole-set validation semantics. ODTS is what an OSDS or ODCS taxonomy link resolves to.
3. **Adopt Fideslang's format.** ODTS keeps its dot-path keys and lifecycle metadata, but the format has no envelope, so an artifact cannot self-identify, be version-pinned, or declare its semantics. Fideslang-derived taxonomies are directly expressible in ODTS.
4. **Inline taxonomies in each contract.** A taxonomy cited by hundreds of contracts is one governed object; inline copies drift. [RFC-0053](https://github.com/bitol-io/tsc/pull/81) settled identification-by-reference; ODTS is the referenced side.
5. **Status quo (documentation URLs).** A URL to a PDF identifies a taxonomy but verifies nothing.
6. **Reference by unique identifier (ODPS `contractId` pattern).** [RFC-0009a](approved/odcs-v3.1.0/0009a-ref-identify-external-contract.md) weighed registry-resolved identifiers and chose file/URL references; a taxonomy's `name` is also the prefix on every cited term, so the reference key and the human-visible binding stay one string. The envelope `id` remains for registries.

## Consequences

- A new ancillary standard per the Bitol roadmap's incubation pattern (draft v0.8.0; retired if inactive a year). No existing standard changes.
- [RFC-0038](approved/odcs-v3.2.0/0038-context.md) links and [RFC-0053](https://github.com/bitol-io/tsc/pull/81) declarations gain resolvable targets, with no amendment to either; Fideslang-derived and internal taxonomies are directly expressible; ISO-derived taxonomies publish equivalence as mappings.
- Follow-up work enabled: additional types, policy annotations, declared extension, ODPS product-level term fields (making the ranked roll-up checkable at product level).
